## 3. 官方資料包（seed data）自動合併 — 設計審核與分階段方案

**結論：這個概念好、且與現有架構高度契合**，因為 `legacy_import` 已經有「ATTACH + `INSERT OR IGNORE` 非破壞合併」引擎可重用。核心把它從「使用者舊 DB」推廣到「官方 seed DB」，但**表白名單要收更緊**。

### 3.1 資料包放哪
- **放進 `_internal/seed/`**（PyInstaller `spec` datas → `resource_root()/seed`），**不要放 exe 旁的 `data/`**。理由：
  - 更新器 `robocopy /XD data` 會**排除** `data/` → 放 `data/` 的新 seed 換版時不會被更新；放 `_internal` 則每次自我替換都會換到新 seed。
  - 避免和「live data（LOCALAPPDATA）」「exe 旁 seed」三者混淆。
- 順帶修 **L5**：目前 `build_release.bat:21-24` 把 seed DB 同時放 `_internal/data`（spec）**和** exe 旁 `data/` → **seed 打包兩份**，zip 變大。改成只留一份（建議 `_internal/seed`）。

### 3.2 manifest（`_internal/seed/manifest.json`）
```json
{
  "data_snapshot_version": 20260701,   // 單調遞增(用日期即可)，合併的 gate
  "generated_at": "2026-07-01T00:00:00Z",
  "app_min_version": "2.0.2",
  "sha256": "<seed.sqlite3 的雜湊>",
  "tables": {
    "daily_prices": {"rows": 1234567, "date_min": "2025-07-01", "date_max": "2026-06-30", "stocks": 1900},
    "institutional_trades": {"rows": ..., "date_max": "..."},
    "dividend_records": {"rows": ...}, "...": {}
  }
}
```

### 3.3 判斷「本地比較舊」
- **主 gate**：本地存 `seed_applied_version`（放 `app_cache` 或一個 marker 檔）。啟動時 `seed.manifest.data_snapshot_version > seed_applied_version` 才合併 → **每版 seed 只合併一次**。
- 由於合併是**純新增**，就算判斷寬鬆也不會壞資料；version gate 只是避免每次啟動白做。
- （可加輔助：比對 `local.max(daily date) < seed.date_max` 當額外訊號，但非必要。）

### 3.4 怎麼 merge 不 replace
- 重用 `import_legacy_data` 的作法，但**參數化表白名單**：`ATTACH seed → 每個允許表 INSERT OR IGNORE(共同欄位) → DETACH`。
- `INSERT OR IGNORE` 以 PK 為準（`daily_prices` PK=(stock_id,date)）→ **本地已有的列一律保留、只補本地缺的列** → 完全符合「永不覆蓋、不刪」。

### 3.5 哪些表可自動補 / 絕對不能碰
- **可自動補（市場公開資料）**：`daily_prices, institutional_trades, dividend_records, market_valuations, monthly_revenues, financial_statements, stock_profiles, data_coverage`。
- **絕對不能碰（使用者私有）**：`watchlist, portfolio_transactions, chart_annotations, indicator_prefs`，以及 `app_cache, bulk_progress`。→ 定義 `SEED_MERGE_TABLES` 白名單（= legacy 白名單**減掉**這四張使用者表）。seed DB 本身也**不該包含**這些表。

### 3.6 要不要先備份本地 sqlite
- **要**（雖然合併非破壞，仍是便宜保險）：合併前把 `LOCALAPPDATA/.../stock_translator.sqlite3` 複製到 `…/backups/stock_translator.<snapshot_version>.sqlite3`，只保留最近 2~3 份。萬一 ATTACH/磁碟異常也能還原。

### 3.7 首次啟動做還是每次都做
- **每次啟動都「檢查」**（讀 manifest+marker，極便宜），**只有 version 前進才「合併」**。合併放**背景執行緒、DB ready 之後**，不可卡 UI／啟動。

### 3.8 避免資料包太大
- seed **只放約 1 年日線**（廣度底，不是 5 年）；深歷史留給「補這檔」。
- seed DB 先 `VACUUM`；只留必要欄位。
- **去重**（§3.1 L5，別打包兩份）。
- 若仍大，Phase 4 再考慮「差量 seed（只帶上次以來的新資料）」，但複雜、先不做。

### 3.9 失敗時 UI 白話
- 背景、非阻斷。失敗 → **安靜保留本地資料**（無害，因非破壞）+ log；最多一行淡色「官方資料包這次沒套用成功，不影響你的資料」。成功 → 可選一行「已補上官方資料包的 N 筆新資料」。**永遠不要嚇到使用者。**

### 3.10 與既有機制如何共存
- **seed 合併**＝安裝/更新時補「歷史底」；**全市場下載**＝把「最新日」補齊（top-up）；**補這檔**＝單檔深歷史。三者互補、都非破壞。
- **順序**：啟動時先 `migrate_legacy_data`（使用者自己的舊資料優先）→ 再 seed 合併（補官方缺的）→ 兩者都 OR IGNORE，無衝突。
- **跟自動更新天生搭配**：seed 在 `_internal` 內，換版就換到新 seed → 下次啟動自動補新 → 使用者**不必手動全市場下載也能長期保鮮**。

### 建議分階段
1. **Phase 1（只出貨，不合併）**：build 產生 capped(1yr)+VACUUM 的 `seed.sqlite3` + `manifest.json`，打包進 `_internal/seed`；去掉重複打包。
2. **Phase 2（合併引擎）**：把 `import_legacy_data` 泛化成 `merge_sqlite(source, target, tables)`；新增 `seed_merge`（白名單、version gate、備份、背景）。接到啟動流程。
3. **Phase 3（UI/設定）**：app-info 顯示「資料包版本」；成功/失敗淡色提示；可選「重新套用官方資料包」。
4. **Phase 4（可選）**：差量 seed 縮小 zip。

## 5. 我認為不該做的事（及原因）
1. **seed 合併不要用 `OR REPLACE` 市場表** → 會覆蓋使用者本地（可能較新/已人工修）的資料，違反「永不覆蓋」。用 `OR IGNORE`。
2. **seed 絕不帶／不合併 watchlist、portfolio、annotations、設定** → 那是使用者心血，覆蓋等於毀資料。
3. **seed 不要放 exe 旁 `data/`** → 更新器 `/XD data` 會跳過它、且與 live/legacy data 混淆。放 `_internal/seed`。
4. **seed 不要出 5 年全市場全深度** → zip 爆大、下載痛、未簽章的 SmartScreen 信譽更難養。1 年廣度底即可，深度交給補這檔。
5. **seed 合併不要同步卡啟動 / 不要每次都真的合併** → 背景 + version gate。
6. **不要 force-move 已發佈 tag、不要同版號 clobber 出兩包** → 每次變更 bump 版本（見記憶）。
7. **這次不要做大型重寫** → 你已要求；且目前架構健康，只需「補發佈、補 H2、做 seed 分階段」即可。
