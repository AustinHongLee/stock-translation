# 18. 日線資料同步架構重設計（發散 → 收斂）

日期：2026-07-03。範圍：日線下載與本地資料維護（STOCK_DAY_ALL / STOCK_DAY / 官方資料包 / data_coverage / bulk）。
前提：不加新依賴、不動 `twse_calendar` / `market_calendar` 節假日判斷、git 由 Codex 操作。

---

## 0. TL;DR

推薦組合：**方案 B（freshness × depth 雙軸）當骨幹**，方案 A 是它的第一步，方案 D（官方資料包 baseline）收編「第一次建庫」情境，方案 C 只取「per-stock sync profile」與「雙進度條」兩個零件，方案 E 不做。
P0 一句話：把「歷史夠不夠深」從魔術常數 `row_count <= 5` 改成用 `listed_date` + 交易日曆**推導出來的期望筆數**，並讓全市場下載的 skip/backfill 都看這個值。

---

## 1. 事故解剖：為什麼 `row_count <= 5` 是止血，不是解法

事故鏈：STOCK_DAY_ALL top-up 先寫入最新 1~2 天 → `latest_date >= target` → 舊版 `plan_data_gap` 判 `current` → bulk `skip()` 標 done → 歷史回補永遠不會發生。

止血法（`TOP_UP_ONLY_DAILY_ROW_THRESHOLD = 5`）擋住了「剛受災」的股票，但留下兩顆殘餘地雷：

1. **門檻會被 top-up 自然沖過**（top-up 寫入只發生在 bulk 的 prelude/on_finish；「更新雷達」只寫 JSON 快照不寫 daily_prices，已核對）。兩條路徑：
   (a) 止血法上線**前**的受災期間，受災股被判 current 跳過，但每次全市場下載的 top-up 仍替它 +1 筆——若受災期橫跨 ≥5 個交易日的下載，這批股票今天 `row_count ≥ 6`，止血法已經管不到；
   (b) 止血法上線**後**，若歷史回補持續失敗（限流/斷線）而 top-up 持續成功，約 5 次下載後同樣越過門檻。
   無論哪條，越過 5 之後被判 `current`，歷史從此不再回補；手動個股同步也會回「已是最新」。
   健檢 SQL：`SELECT stock_id, row_count, earliest_date, latest_date FROM data_coverage WHERE node='daily_price' AND row_count BETWEEN 1 AND 60 ORDER BY row_count;`
2. **真・新上市股 ping-pong**。上市 3 天的股票永遠 `row_count <= 5` → 每次全市場下載都 `force_refresh_required` → 以 365 天 lookback 重抓 13 個月（幾乎全空）→ 抓完仍 3 筆 → 下次再重抓。浪費 API、加重限流風險。

共同根因：**單一 `status` 軸把「最新度」和「歷史完整度」混在一起**，再用常數去猜深度，而不是推導「這檔股票在這個時間窗**應該**有幾筆」。

現況中值得保留的好資產：`sync_one` 收尾用「本地實際最後一筆日期」驗收才標 done（防半套資料）；T86 空日不標 done；`skip()` 不信任歷史 done 而是重算 coverage；`data_coverage` 已存 `earliest_date/row_count/hole_count`；`stock_profiles.listed_date` 已經有了；官方資料包 pipeline（`build_official_data_pack.py` + `seed_merge.py`）已能用。

## 2. 發散：五種設計方案

### 方案 A：最小改動 — 把深度門檻從常數變成可推導

**核心概念**：保持單軸 status，但把 `row_count <= 5` 換成：
`expected_days = count_twse_trading_days(max(listed_date, target - 365d), target)`，`row_count` 顯著低於 `expected_days` 才算淺。同時 backfill 抓取窗口起點改為 `max(listed_date, target - 365d)`。

- **優點**：diff 極小（`data_gap.py` + 兩個呼叫端傳 `listed_date`）；一次拆掉上面兩顆雷；純函式、好測。
- **代價**：單軸語意仍混濁，「已最新但歷史淺」對 UI 仍不可表達；修的是症狀集合，不是概念。
- **改動範圍**：`data_gap.plan_data_gap`（加 optional `listed_date` 參數）、`bulk_runner`、`service.py` 傳參、測試。
- **踩雷處**：停牌／零成交造成的合法缺洞 → 比例門檻要寬鬆（見方案 B 的 0.5/0.9）；`listed_date` 可能為 None（TPEX 或 catalog 缺）要 fallback 到現行行為。
- **適合現在做嗎**：**是**。不管選哪個大方案，這一步都是第一步。

### 方案 B：coverage 雙軸 — freshness × depth（推薦骨幹）

**核心概念**：把 coverage 拆成兩個獨立、**推導出來（不儲存為真相）**的軸：

- **freshness**（最新度）：`latest_date` vs `target`（沿用現行 current / gap / source_pending + 寬限日邏輯，不動）。
- **depth**（歷史完整度）：`depth_ratio = row_count / expected_days`，其中 `expected_days` 用 `listed_date` 與交易日曆推導（同方案 A）。分級：
  `empty`(0 筆) → `latest_only`(earliest 距 target ≤ 7 個交易日) → `shallow`(ratio < 0.5) → `usable`(0.5 ≤ ratio < 0.9) → `deep`(≥ 0.9)。

使用者提的 coverage state machine 八態，其實是這兩軸的**外積再加來源狀態**，對照如下：

| 使用者提議的狀態 | 雙軸下的位置 |
|---|---|
| empty / latest_only / shallow / usable / deep | depth 軸的五級 |
| stale | freshness 軸（latest < target 超過寬限） |
| source_pending | target 尚未公布／寬限中（freshness 軸既有） |
| unsupported_or_suspended | 失敗記憶（連續 N 次補不到），屬 sync profile（方案 C 零件），不是 coverage 軸 |

**刻意不儲存八態單一欄位**：存起來的狀態會過期、會漂移（這次事故本質就是「存了一個混合語意的狀態然後信了它」）。兩軸各自可以從 `daily_prices` + `listed_date` + 日曆隨時重算，顯示狀態只是 `f(freshness, depth)` 的投影。

**行動決策矩陣**（取代現在的 if 巢狀）：

| | depth ≥ usable | depth < usable |
|---|---|---|
| **fresh** | 無事（skip） | historical backfill（本次事故案例落在這格） |
| **stale（小 gap）** | gap patch（只補缺日） | backfill（一次拉滿 horizon，順便補最新） |
| **stale（大 gap）** | force refresh | backfill |
| **empty** | — | initial backfill（優先建議套官方包） |

**STOCK_DAY_ALL 的定位在此方案下自動成立**：它是「快速索引／最新價來源」——寫入照舊（upsert 冪等，`source` 欄已標 `TWSE_STOCK_DAY_ALL`），但它**只能推高 freshness，永遠不能滿足 depth**。不需要任何特殊標記，因為 depth 是從筆數推導的，top-up 加一筆推不動 ratio。

- **優點**：修掉的是「整類 bug」（任何單軸混淆）；UX 可以誠實顯示兩件事（「最新 ✓／歷史 42%」）；全部 stdlib；沿用既有表，P0 甚至不需要 schema migration（payload 即時算，P1 才落欄位）。
- **代價**：`plan_data_gap` 介面變動，讀 `coverage["status"]` 的地方（web api、local_data、UI 文案）要跟著理解新欄位；測試面擴大。
- **改動範圍**：`data_gap.py`（新增 `assess_daily_depth()` 純函式 + 行動矩陣）、`bulk_runner.skip/sync_one`、`service.py`、`web/api.py` local_data payload、UI 文案、測試。約 5 檔核心 + 測試。
- **踩雷處**：(1) `expected_days` 必須從 `horizon_start` 起算而**不是** `earliest_date` 起算——用 earliest 起算會自我安慰（top-up-only 股 earliest≈latest，ratio≈1 → 誤判 deep）。(2) 停牌股容忍度靠 0.9 門檻吃掉零星停牌；長期停牌是 freshness 軸的事。(3) `usable` 門檻是產品決策：圖表／結構指標需要多少天才有意義（MA240 需要 240+ 交易日 → deep；基本圖 60 天可用）。(4) institutional 節點先不套 depth，維持現狀，避免一次改兩個節點。
- **適合現在做嗎**：**是，這是推薦骨幹**。P0 做核心，P1 補 UI 與欄位。

### 方案 C：job queue / scheduler — 任務型同步

**核心概念**：顯式任務分類（daily top-up / historical backfill / gap patch / repair / verification）落成 SQLite jobs 表；`BulkDownloadManager` 變成 worker 抽隊列；per-stock sync profile（上市日、最近成功月份、失敗月份、next_retry_at、退避倍數）；checkpoint 到「月」粒度（13 個月的 backfill 斷在第 7 個月，重跑從第 8 個月續）。

- **優點**：斷點續傳細到月；失敗退避讓爛股不再每次擋路；兩條進度條天然成立（按 job type 分組計數）；未來加 TPEX／新來源時是正確的骨架。
- **代價**：本專案最大的 diff；併發、冪等、崩潰後殭屍任務（要 lease/heartbeat）、與 `bulk_progress` 的雙帳本問題（必須取代它而不是共存，否則兩邊狀態漂移）；對單機單人 app 而言，現有 manager（暫停／停止／連續失敗自動暫停／retry_failed_only）已覆蓋七成需求。
- **改動範圍**：新表 + 新模組 + 改寫 bulk_runner/bulk.py + web 狀態 API + 大量測試。3~5 天起跳。
- **踩雷處**：SQLite 單寫者與 UI 執行緒搶鎖；job 飢餓；過度設計（docs/06 已警告過這個傾向）。
- **適合現在做嗎**：**整套不做**。抽兩個零件：(1) `sync_profile`（P1，一張小表就夠，不需要隊列）；(2) 進度按「補最新／補歷史」分兩條呈現（P0 可先用文案版）。

### 方案 D：官方資料包 baseline + 增量同步

**核心概念**：把已存在的官方資料包（`--apply-seed` 只增不覆蓋 + 強制套用）升級為「depth 的主要來源」：第一次建庫先套包（深歷史零 API 成本），網路同步從此只負責 freshness top-up 與小 patch；每次 release 隨附新包，最壞情況的 backfill 從「13 個月 × 千檔」縮成「包日期之後 × 缺的檔」。

- **優點**：結構性解掉「第一次建資料庫」這個最大限流風險；離線友善；pipeline、sha256、版本閘（`app_min_version`）、開機自動 merge 全都已經存在——這是唯一「做一半白送」的方案；發佈通道（更新器）也現成。
- **代價**：營運負擔（每次發版要重建包——但你本來就在做）；包有時滯，套完仍需增量；depth 偵測仍然必要（判斷包沒涵蓋到的股票），所以它不取代 B，只是餵飽 B。
- **改動範圍**：主要是 UX 接線：空庫時 app 內主動引導「先套包再增量」，而不是靠使用者自己找 .bat。後端幾乎不動。
- **踩雷處**：(1) `SEED_MERGE_TABLES` 含 `data_coverage`，only-add merge 會把**包製作當天的 status/target** 帶進來——因為 plan/skip 都會 `refresh_data_coverage` 重算所以無害，但「不要信包裡的 coverage 狀態」要寫成註解＋測試釘住，防止未來有人短路重算。(2) 除權息：TWSE STOCK_DAY 是未還原價，歷史列基本不可變，only-add 安全；但若來源回頭修數據，only-add 永遠不會修正——這是接受的取捨，交給 P2 verification job。
- **適合現在做嗎**：**P1**。P0 不動後端，P1 做空庫引導 UX；P2 才考慮 app 內自動下載新包。

### 方案 E：本地資料湖 / source ledger（激進）

**核心概念**：append-only 抓取帳本（每次 fetch 記 source、參數、範圍、筆數、結果 hash）；`daily_prices` 已有 `source`/`fetched_at` 欄，再加衝突偵測（同日不同價）與 replay/diff 式 repair；coverage 全部變成帳本的物化視圖。

- **優點**：完美可稽核（「這檔為什麼只剩兩天」一條 query 回答）；能做來源交叉驗證；來源優先權規則顯式化。
- **代價**：對單機個人 app，回報主要是 debug 體驗；schema 大改、寫入放大、帳本膨脹；90% 的稽核需求現在就能用 `source` 欄 + `sync_runs` + `bulk_progress` 拼出來。
- **改動範圍**：全面。
- **踩雷處**：正是 docs/06「過度設計」點名的那種工程；複雜度預算花在這裡不如花在 UX。
- **適合現在做嗎**：**否**。只抽一個零件：P2 的抽樣 verification job（隨機 N 檔，拿 STOCK_DAY 單月對 STOCK_DAY_ALL 同日列交叉核對，不一致列入 repair 清單）。

## 3. 收斂：對五個情境的統一回答

| 情境 | 策略 |
|---|---|
| 第一次建資料庫 | 引導套官方包（D）→ 增量 top-up + 對包外股票 backfill（B 判定） |
| 日常補最新 | STOCK_DAY_ALL 一發（freshness 來源），個股缺口才用 STOCK_DAY 小 patch |
| 個股手動同步 | 同一個行動矩陣：fresh+deep 顯示「已是最新且完整」；fresh+shallow 給「補歷史」按鈕 |
| 全市場下載 | 兩階段：①補最新（prelude，一次全市場）②補歷史（只跑 depth < usable 的檔）；進度分開顯示 |
| 官方資料包 | baseline：只增不覆蓋，套完一律重算 coverage，不信包內狀態 |

## 4. 落地優先級

**P0（必做，1~2 天，全 stdlib）**
1. `data_gap.py`：新增 `assess_daily_depth(coverage, listed_date, target)` 純函式（回 level + expected/actual）；`plan_data_gap` 用 depth 取代 `row_count <= 5` 特例（對外可沿用 `STATUS_FORCE_REFRESH_REQUIRED` 語彙，少破壞消費端）。
2. backfill 抓取窗口起點 = `max(listed_date, target - lookback)` → 新上市股不再空抓 13 個月。
3. `bulk_runner`：`skip()` 只在 fresh **且** depth ≥ usable 才跳過；`prelude` 抓 profiles 時把 `listed_date` 放進 ctx map 供逐檔查（注意 `retry_failed_only` 模式不跑 profiles → 改由 store 查，查不到就 fallback 現行行為）。
4. 防回歸測試（見 §6），既有測試全綠。
5. UX 低配版：bulk status message 分兩行文案（「① 補最新收盤：完成」「② 補歷史：n/m 檔」）；local_data 每檔加「歷史完整度」欄位（即時算，不動 schema）。

**P1（可做）**
6. `sync_profile` 小表：stock_id、listed_date 快取、last_backfill_month、failed_months、next_retry_at、attempts → 失敗退避 + 月粒度 checkpoint（從方案 C 抽出，不建隊列）。
7. 空庫引導 UX（方案 D）：app 內偵測空庫 → 建議套官方包 → 再增量。
8. `data_coverage` 落 `depth_level/expected_days` 欄位（ALTER TABLE ADD COLUMN），local_data 頁不必每次重算。
9. backfill 排序：depth 最淺的先補（最壞的先痊癒）。

**P2（以後）**
10. 抽樣 verification job + repair 清單（方案 E 零件）。
11. app 內自動抓最新官方包；institutional 節點套 depth 軸；TPEX。

**如果只允許 1~2 天**：
- Day 1：上面 1+2 + 深度真值表測試（純邏輯零 I/O，最快可驗證）。
- Day 2：上面 3+4+5（接線 + payload + 文案 + bulk 測試）。
- 砍法：時間不夠先砍 5 的 local_data 欄位，只留 bulk 兩行文案；`sync_profile` 一律不擠進這兩天。
- 注意：**depth 邏輯上線前不要撤 `row_count <= 5` 止血法**；上線時由 depth 規則自然取代（它是止血法的嚴格超集）。受災的 6~30 筆股票不需要修復腳本——新 `skip()` 會判 shallow 自動回補，自癒。

## 5. UX 白話設計

- 本地資料頁每檔兩個徽章：「最新：✓ 已到 7/2」＋「歷史：只有 12 天／約一年 ✗（可補齊）」，後者附一鍵補歷史。
- 全市場下載進度兩條：「① 補最新收盤：完成（1,023 檔一次補齊）」／「② 補歷史：132 / 188 檔（預估 9 分鐘）」。失敗清單維持現有三分法：來源未公布（source_pending，稍後自動再試）／可重試失敗／持續失敗。
- 第一次開啟（空庫）：「你的資料庫是空的。最快：套用官方資料包（約 1 分鐘，離線可用）；或直接全市場下載（約 X 分鐘）。」
- 文案原則：不要跟小白講 freshness/depth，講「最新」和「歷史夠不夠」。

## 6. 測試策略（重點：防「只有最新 1~2 天卻被當完成」回歸）

1. **不變量掃描測試（最重要的一條）**：`for row_count in 1..40`，構造 `latest == target`、`earliest` 很近的 coverage → `plan_data_gap` **永遠不得**回 `current`，除非 depth ≥ usable。用迴圈掃參數空間，防止未來任何人把常數門檻改回去（不管常數是 5 還是 50 都會被抓到）。
2. **累積沖過門檻案例**（現行止血法的已知漏洞）：row_count=10、earliest=target−13 個交易日、latest=target、listed_date=2010 → 必須要求 backfill。
3. **新上市不 ping-pong**：listed_date=target−3 個交易日、3 筆、latest=target → 判 deep/current，**不得** force refresh；若真要抓，fetch_start 必須 ≥ listed_date（斷言 `price_ranges`）。
4. **top-up 不推 depth**：空庫 → 模擬 STOCK_DAY_ALL 寫入 1 筆最新 → `skip()` 必須 False；backfill 後才 True（`test_latest_all_single_row_does_not_skip_history_backfill` 已有，保留並擴充到 6+ 筆版本）。
5. **停牌容忍**：expected 100、actual 93（零星停牌）→ deep，不觸發回補；actual 40 → shallow。
6. **listed_date=None fallback**：行為退回現行邏輯，不炸。
7. **驗收邏輯不動**：sync_one 仍以「本地實際最後一筆 ≥ target」為 done 條件（既有測試已鎖）。
8. **seed 套用後不信包內狀態**：merge 後 plan/skip 重算 coverage（釘住 §2-D 踩雷 1）。
9. 節假日相關一律沿用 `count_twse_trading_days` 既有測試，不新增節假日 fixture（遵守不動日曆的約束）。

## 7. 明確不做

- 不引入任務隊列框架、不加排程器執行緒（現有 manager 夠用）。
- 不儲存八態混合狀態欄位（狀態一律推導）。
- 不動節假日判斷、不動 T86 邏輯、不動除權息口徑。
- 不做資料湖／帳本重構。
